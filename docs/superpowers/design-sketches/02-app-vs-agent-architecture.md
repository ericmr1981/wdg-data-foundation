# WDG — Application vs Agent 关系对比

> 在动手前必须先定一件事:Agent 是"UI 里的一个按钮",还是"独立服务,UI 只是它的一种客户端"?
> 这个选择决定后续所有架构。

## 对比:两种架构

### 架构 A — "Agent 是 UI 里的一个按钮"  (附属品模式)

```
┌─────────────────── Next.js UI (port 4100) ─────────────────────┐
│                                                                 │
│  /u/financial    /u/rules    /u/approvals    /u/dashboard        │
│       │             │            │                │             │
│       └──────┬──────┴────────────┴────────────────┘             │
│              │                                                    │
│         ChatDrawer  (浮窗,UI 的一个组件)                          │
│              │                                                    │
│         /api/chat  (Next.js API Route,一个普通的 endpoint)        │
│              │                                                    │
│         调用 Anthropic API, 拼装 system prompt + MCP tools       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

特点:
- Agent 完全被 Next.js 进程托管
- 用户只能在 UI 里跟它对话
- Agent 没有"独立生命":UI 关掉它就停
- 加新渠道(钉钉/企微/定时任务)需要重新打包部署
```

### 架构 B — "Agent 是独立服务,UI 是它的客户端之一"  (服务模式) ← 推荐

```
┌─────────────────── Next.js UI (port 4100) ─────────────────────┐
│                                                                 │
│  /u/financial    /u/rules    /u/approvals    /u/dashboard        │
│       │             │            │                │             │
│       └──────┬──────┴────────────┴────────────────┘             │
│              │                                                    │
│         ChatDrawer  ←──── UI 是 Agent 的"客户端之一"             │
│              │                                                    │
└──────────────┼──────────────────────────────────────────────────┘
               │  HTTP / WebSocket
               ▼
┌─────────────────── Agent Service (独立进程) ───────────────────┐
│                                                                 │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐     │
│  │ Channel  │   │ Channel  │   │ Channel  │   │ Channel  │     │
│  │  Web UI  │   │  Cron    │   │  钉钉    │   │  Webhook │     │
│  └────┬─────┘   └────┬─────┘   └────┬─────┘   └────┬─────┘     │
│       └──────────┬───┴──────────┬───┴──────────┬───┘            │
│                  ▼             ▼             ▼                  │
│         ┌────────────────────────────────────────┐              │
│         │      Conversation / Task Router        │              │
│         └────────────────┬───────────────────────┘              │
│                          ▼                                       │
│         ┌────────────────────────────────────────┐              │
│         │       Agent Core (LLM + Tools)         │              │
│         │                                        │              │
│         │  · 短期记忆 (per-conversation)         │              │
│         │  · 长期记忆 (per-user, per-brand)      │              │
│         │  · 任务队列 (long-running tasks)       │              │
│         │  · MCP tools (调用既有 45 个)          │              │
│         └────────────────┬───────────────────────┘              │
│                          ▼                                       │
│         ┌────────────────────────────────────────┐              │
│         │   Memory / Task / Audit Store (PG)     │              │
│         └────────────────────────────────────────┘              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

特点:
- Agent 是独立进程,有自己的生命周期 (24/7 在跑)
- UI 只是一个 Channel,加钉钉/企微 = 加一个 Channel Adapter
- 定时巡检 (Cron Channel) 主动跑任务,不需要人触发
- 长期记忆 / 任务队列有持久化
- 复用既有 45 个 MCP tools, 不重写
```

## 关键决策点

| 维度           | A 模式 (UI 内嵌)    | B 模式 (独立服务) |
|----------------|---------------------|-------------------|
| 改造量         | 小 (1-2 周)         | 中 (3-5 周)       |
| 长期可扩展性   | 差 (新渠道要重打包) | 好 (加 adapter)   |
| 主动能力       | 弱 (需要 UI 触发)   | 强 (Cron/Webhook) |
| 记忆持久化     | 难 (绑 Next.js 进程)| 易 (PG/SQLite)    |
| 任务队列       | 无                  | 原生              |
| 调试性         | 简单                | 稍复杂 (跨进程)   |
| 部署           | 一个进程            | 两个进程          |

## 我的强烈推荐: B 模式

理由:
1. **你刚才列的四件基础能力** (沟通/记忆/任务队列/关系) 几乎都不可能优雅地在 Next.js API Route 里实现
2. MCP tools 已经独立了 (45 个 JSON-RPC tools),Agent 层独立是顺势而为
3. 未来加钉钉/企微/Webhook 不用动 UI 进程
4. 定时巡检 / 批处理是 Agent "主动" 的前提,必须独立进程
5. 现有 ChatDrawer 可以保留,**作为 B 模式的一个 Channel**,不是删除,是降级为"客户端"
